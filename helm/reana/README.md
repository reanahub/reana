# REANA: reproducible research data analysis platform

## Chart Prefix

This Helm automatically prefixes all names using the release name to avoid
collisions.

## Authentication

The chart does not deploy an identity provider by default. Configure an external
OIDC issuer with the `auth` values and provide
`secrets.auth.REANA_AUTH_WEB_CLIENT_SECRET` when `auth.bffEnabled` is true. The
profiles in `helm/configurations/values-cern.yaml`, `values-eosc.yaml`, and
`values-escape.yaml` provide issuer-specific starting points without client
credentials.

The local ESCAPE IAM seed creates one client for both browser and device-code
flows. Supply the `reana_client.client_id` printed by the seed as both
`auth.clientId` and `auth.webClientId`, and supply its `client_secret` as
`secrets.auth.REANA_AUTH_WEB_CLIENT_SECRET`; the exact deployment command is
documented at the top of `helm/configurations/values-escape.yaml`.

`reana-dev cluster-deploy` cannot discover an external identity's immutable
subject. It therefore completes database setup without creating the
administrator and prints the `flask reana-admin create-admin-user` command to
run with the issuer and subject before that administrator's first REANA login.

Bundled Keycloak is intended primarily for local development and small test
deployments. It has one replica, so production deployments should still use a
separately operated identity provider. When enabled, Keycloak defaults to a
dedicated database and role on the chart's bundled PostgreSQL service. External
PostgreSQL is supported with `keycloak.database.mode=external`; the database and
role must already exist. The embedded database is available only through the
explicit `keycloak.database.mode=ephemeral` development opt-in, and Helm emits a
warning because replacing the pod loses identities and signing state. Keycloak
is enabled and configured by `helm/configurations/values-dev.yaml`; the chart
defaults keep it disabled and do not include a seeded user or default
administrator credentials. The public issuer always uses HTTPS.
`values-dev.yaml` deliberately opts into the bundled Keycloak's in-cluster HTTP
backchannel, which REANA Server restricts to the exact generated Service and
realm base. This exception is not production transport evidence. External and
production-style deployments use verified HTTPS by default; private issuers can
provide a CA bundle path with `auth.caBundle`.

The bundled PostgreSQL default is version 14.23. Installations whose persistent
volume was initialised by PostgreSQL 12 must perform a PostgreSQL major-version
migration before adopting this image; changing the image tag alone is not a
database migration. PostgreSQL 14.x installations can take the 14.23 minor
update without changing the on-disk major format.

On every Helm install or upgrade, a bounded post-deployment job reapplies the
bundled realm roles, protocol mappers, redirect URLs, audience, and client
credentials with Keycloak's partial-import overwrite policy. This keeps a
persistent realm aligned with chart values; Keycloak's startup import alone only
creates realms that do not already exist. Keep the bootstrap administrator
Secret stable so that subsequent chart upgrades can authenticate this job. The
same reconciliation makes `offline_access` a default realm role: the Python and
Go CLI clients request that optional scope so persisted logins can refresh after
the ordinary SSO session expires. The separate configured `required_role` still
controls whether a Keycloak identity may access REANA.

## Custom Jupyter images

REANA starts interactive Jupyter sessions with `start-notebook.sh` and injects
the random per-session access token through the `NOTEBOOK_ARGS` environment
variable. Administrators who enable
`interactive_sessions.environments.jupyter.allow_custom` must therefore admit
only images that implement the Jupyter Docker Stacks launch contract: the image
must provide `start-notebook.sh`, and that launcher must pass `NOTEBOOK_ARGS` to
Jupyter. An image that ignores this variable would start without REANA's
per-session access control and must not be allowed.

REANA owns `NOTEBOOK_ARGS`, `NB_GID`, `NB_UMASK`, and `REANA_WORKSPACE` for
interactive sessions. User-secret configuration cannot override these reserved
variables. The notebook token is stored in a dedicated Kubernetes Secret and is
not included in the pod's command-line arguments.

Before upgrading, rename any user secrets that use these reserved names.
Existing collisions are rejected when an interactive session starts; this
prevents user-controlled values from replacing the security-sensitive runtime
configuration.

**Known residual exposure of the session URL.** Opening a session still requires
putting that same token in the browser's URL bar as a `?token=...` query
parameter — that's inherent to how Jupyter authenticates a fresh request, not
something REANA controls. Two consequences to be aware of:

- The URL (token included) is written to the browser's local history, outliving
  the session's own lifetime.
- Any reverse proxy or ingress controller in front of the deployment that logs
  full request URIs (the common default access-log format) will record the token
  in its own logs the moment the session is opened.

This chart closes the one sub-vector fully within its control — a
Referrer-Policy: no-referrer middleware on every interactive-session Ingress
(see `reana-session-headers-middleware.yaml`), so the token cannot also leak via
the Referer header if the notebook page loads a cross-origin subresource.
Closing the other two would need a redesign of how the session is handed off
(e.g. a one-time cookie exchange instead of a bearer-in-URL token) rather than a
chart-level mitigation. Deployments with strict requirements here should
configure their ingress controller's access-log fields to exclude or redact
query strings for session paths.

## Uninstalling

`helm uninstall` intentionally leaves the chart's Secrets in the cluster
(`helm.sh/resource-policy: keep`) — this includes the database credentials, the
bundled Keycloak database and OIDC client credentials, and every other generated
Secret, not only the auth-related ones. This is deliberate: a reinstall reuses
the same credentials rather than generating new ones and losing access to
existing data. The chart does not label its resources by Helm release, so a full
purge after uninstalling has to match by the same name prefix every resource
uses (the release name, e.g. `reana` below):

```console
$ kubectl get secrets -o name | grep '^secret/reana-' | xargs --no-run-if-empty kubectl delete
```

## Configuration

### Sandbox isolation prerequisites

The workflow specification validator executes untrusted workflow-loading code.
Its sandbox creates a Kubernetes `NetworkPolicy` before starting, so the cluster
must use a CNI plugin that enforces NetworkPolicy. Applicable policies combine
additively; ensure that no other policy selecting validator pods widens their
egress. Standard NetworkPolicy also permits traffic to the node on which the pod
runs, so multi-tenant installations should use a CNI or host firewall that can
filter host endpoints, or schedule validators on dedicated hardened nodes. An
accepted policy object alone does not prove isolation; operators should verify
forbidden egress on their supported cluster configuration.

Run the live enforcement test after deploying REANA. The final argument states
whether the validator is expected to retain access to the public internet. Both
verification scripts require an OIDC access token:

```console
$ REANA_ACCESS_TOKEN="<OIDC-access-token>" \
    scripts/test-spec-validator-network-policy.sh default reana true
```

The validation-snapshot and later input-upload contract can be exercised against
the same live cluster:

```console
$ REANA_ACCESS_TOKEN="<OIDC-access-token>" \
    scripts/test-spec-validation-storage.sh default reana
```

The test triggers specification validation, creates a short-lived pod selected
by the validator policy, and verifies that it cannot connect to either the REANA
server Service or its backing pod. The test reports resident-node access for
information because standard Kubernetes NetworkPolicy does not guarantee that
this traffic is blocked.
